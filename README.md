# astrbot_plugin_dafeiyu_merge · 私聊聚合

AstrBot 私聊消息聚合插件：**连发的多条私聊合并成一条再回复**，她不再逐句抢答，你也不用被她拆着接话。

## 行为

- 私聊第一条消息进入**滑动等待窗**（默认 12 秒）：你每续发一条，倒计时重置；你停手超过窗口时长，她把你这轮说的所有话**合成一条**读取，**只回一次**
- 回复质量更好——她看到的是完整一段，不是碎片
- **合并轮简短回应**（v1.1.0，默认开）：连发合并的那一轮，随 LLM 请求注入一次性提示"对方连发 N 条，像真人那样一两句简短回"——治"你发两条她回六七条被分段刷屏"。单条消息轮不注入、提示不进对话历史，平时回复风格不受影响；模板可改（见下方配置）
- **指令豁免**：以 `/`、`!`（可配置）开头的命令消息直通不等待，干活零影响——按消息链**原文**判定（框架会先剥掉消息文本的唤醒前缀，直接读剥完的文本会误判，v1.1.0 修复）
- **群聊完全不受影响**，一个字节都不碰
- 两道保险：单次聚合最长等 30 秒 / 最多攒 10 条，到顶立即回复，不会一直哑

## 代价（设计如此）

- 单独一条消息也会等满一个窗口（默认 12 秒）——这是"确认你没有下文"的必要等待；嫌慢可调小窗口，代价是接不住隔句较慢的连发
- 不带 `/` 的指令型文字（如"搜索歌曲 X"）同样等满窗口，她照样执行，只是慢半拍

## 和同类方案怎么选（差异说明）

消息聚合类插件市面上不少，主流两种路线：

- **语义判读类**：用语义模型判断"这句说完没有"，说完立刻发——体验最顺滑，但要装模型/依赖、吃资源
- **通用聚合类**：群聊私聊一起管、功能面广，但和群聊管线抢活，配置项也多

本插件走窄门，**只管私聊**：

- **零依赖纯 Python**，拷进去就能跑，不装任何额外包
- **只碰私聊消息**，群聊一个字节不动——天然不和其他群聊插件抢活
- 文字/图片/表情等多模态消息链照常合并
- 指令豁免可配置，`/` 指令零等待直通

坦白讲：想要"句子一说完立刻回"的零延迟体验，语义判读类做得更好，代价是依赖与资源；本插件用固定小窗口换零依赖与共存安全，按你的部署环境挑。

## 配置

| 配置项 | 默认 | 说明 |
|---|---|---|
| `merge_window_seconds` | 12 | 两条消息之间的最大间隔，超过即视为说完（每条新消息重置倒计时）。建议 8~15 |
| `max_hold_seconds` | 30 | 单次聚合最长等待 |
| `max_buffer_messages` | 10 | 单次聚合最多合并条数 |
| `command_prefixes` | `["/", "!"]` | 指令豁免前缀；留空自动跟随平台唤醒前缀 |
| `seg_enabled` | `true` | 私聊分段回复开关（见 v1.2.0） |
| `seg_interval` | `1.2,3.0` | 分段条间随机间隔（秒） |
| `merged_compact_enabled` | `true` | 合并轮简短回应总开关；关=合并后照常长回复 |
| `merged_compact_template` | 见下方 | 简短回应提示词模板，随意改写；唯一变量 `{count}`=当轮合并条数，删掉也能用 |

提示模板默认值：

```
[系统信息-私聊聚合] 对方刚连发了 {count} 条消息，你已一次性全部看到。像真人回消息那样简短：一两句就好，别长篇大论。
```

## 实现说明

依赖 AstrBot 每条消息独立异步处理的特性（事件并发），由 priority=100 的处理器最先拦截：批次首条消息阻塞等待，后续消息并入批次并自截（`stop_event`），窗口耗尽后把所有消息链合并进首条、放行走正常人设/记忆/LLM 管线。被合并的后续消息对其他插件不可见，不会重复记档。

简短回应走 `on_llm_request` 的 `extra_user_content_parts`（`mark_as_temp`）：只在刚发生合并的会话下一次请求注入一次，不进历史、不影响前缀缓存。

## 更新记录

- **1.4.1** 长度纪律改按**平均每行字数**触发：他习惯连发短行（"吃了
我想吃你"总量不过二十字、每行才几个字），按整条字数判"短消息"会漏掉这类——签收式纪律出不了场。现在平均每行 ≤12 字即注入；真正的长段（一行就几十字、讲正事）依旧不打扰。触发文案不变，只换出场时机。测试 +5（连发短行注入/长行不注入/空白防护），28/28
- **1.3.0** **分段不再劈颜文字 + 回复长度纪律注入**：①**切分括号感知**——分段按句末标点/换行切刀，但旧正则不认括号：颜文字内部带 `。？！~…` 的（`(・_・。)`、`(？_？)`、`(~_~)` 这类，实测常见词表 1558 张里 67 张中招）落在切分点上会被拦腰劈成两段气泡发出去。切分器改为括号深度跟踪，括号内的标点不切、括号没闭合时后半不切（宁可不切，不劈脸）；②**长度纪律注入**（`seg_len_enabled`/`seg_len_hint`）——每次私聊 LLM 请求临时注入一小段"短句、别刷屏、（）最多一个"（不进对话历史）。动机：模型回复长篇不是人设没写短句规则，是**上下文里躺着自己几十条长回复当范文**，提示词规则打不过活例子（与颜文字锚定同一病根）；这条每请求在场，跟人设解耦
- **1.2.1** README 增**「和同类方案怎么选」**差异说明：语义判读类/通用聚合类两条路线对比 + 本插件"私聊专用零依赖"定位与坦白短板——只列品类不点名产品，怎么选交给用户
- **1.2.0** 新增**私聊分段回复**：框架的分段回复功能对私聊默认 LLM 路径不生效（实测多句长回复整条发出）。本插件在私聊范围内补齐——LLM 回复按句末标点/换行切分、逐条发送、条间随机间隔（默认 1.2~3.0 秒，可配）；表情包等非文本组件放最后单独一条；指令/工具消息不走此逻辑；群聊不受影响。开关 `seg_enabled`
